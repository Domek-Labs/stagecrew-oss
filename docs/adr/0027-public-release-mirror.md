# ADR 0027 — a gated release mirror: denylist scan as a regular check, one squashed commit per release, no push automation

**Status:** accepted
**Date:** 2026-09-22
**Issue:** #148
**Amends:** `CLAUDE.md` (new "Public release mirror" section), `CONTRIBUTING.md` ("What each check derives from" table, check 7 row), `checks/check-7-release-scan.js`, `checks/release-denylist.json`, `ops/release-mirror.js`, `.env.example`

## Context

stagecrew is developed in a private repo that carries issues, loop history and references to client work. A public edition already exists as a separate, currently-private repo (`Domek-Labs/stagecrew-oss`, one squashed commit of the 2026-09-22 tree, prepared ahead of this issue), but nothing keeps it in sync and nothing stops a private reference from being published by accident. A one-off manual audit found the working tree clean while the development history was not: it carried two employer-repo checkout paths, an employer repo slug, and private host names — none of them written out in this ADR, deliberately (see "What this ADR deliberately does not name" below). A manual audit does not repeat itself; this issue makes publishing a deliberate, gated, machine-checked act.

## Decision

### 1. The private repo stays the source of truth; issues stay private

The public repo is a **publish target**, never a second place development happens. Every issue, every loop-stage comment, every claim label — the entire audit trail this plugin's own loop produces — stays in the private repo. Two reasons, not one: first, a loop comment routinely quotes diff content, file paths and reasoning that has not been through the denylist scan (the scan runs on `syntax_check`, not on issue comments); publishing issues would need a second, differently-shaped gate this issue does not build. Second, the loop's own audit value (claim protocol, revise cycles, ADR cross-links) depends on a stable issue-number space; mirroring issues would mean either forking that space or losing the history the private repo already has 148 issues' worth of.

**Cost, named plainly:** an external contributor filing a GitHub issue against the public repo has nowhere the private loop will ever see it. That is out of scope for this issue (see the "first real mirror run" note in "Standards Notes" of issue #148) and is a real, deliberate limitation of publishing without also opening a triage channel.

### 2. One squashed commit per release, never history transfer

`ops/release-mirror.js` builds exactly one new commit whose **tree** is HEAD's tree (minus the exclusions in decision 4) and whose **parent** is the public repo's current HEAD — via a throwaway git index (`git read-tree HEAD` + `git update-index --force-remove` + `git write-tree`) and `git commit-tree -p <public-head>`, never a `git push` of private commits, a rebase, or a merge.

`git commit-tree -p <public-head>` requires that parent commit object to already exist in the **local** object database, and the private repo never otherwise holds any commit from the public one. A real run therefore reads the public HEAD twice, independently: `git ls-remote` reports the sha, then `git fetch --no-tags <url> refs/heads/<branch>:<throwaway ref>` pulls that commit's object into the local store, and the script verifies the fetched sha matches what `ls-remote` reported before proceeding — refusing rather than guessing if the two disagree (the remote moved in between). The fetch is a full fetch, not a shallow one (no `--depth`): a shallow fetch here would leave `.git/shallow` behind and permanently turn this checkout into a shallow repository, which is a side effect this script must not have on the operator's private clone. The throwaway ref is deleted immediately after. Both reads, and the eventual push, share one `GIT_ASKPASS` token handoff (decision on credential handling, unchanged from the original design) since the target repo is private end to end — an unauthenticated `ls-remote` against it fails exactly like an unauthenticated push would. `--dry-run` never calls `commit-tree`, so it never needs the parent object locally and never fetches; its own `ls-remote` read still uses the token when one happens to be set, and degrades to `"unknown"` when it is not or when there is no network path.

**Rejected alternative: transfer the full private history.** This is the audit's original finding restated as a mechanism — the private history is exactly where the leaked paths were found. A tool that publishes squashed snapshots and a tool that publishes full history are not two settings of the same tool; the latter re-opens the class of leak this issue exists to close, structurally, on every run. Rejected outright, not tuned.

**Cost, named plainly:** the public repo's own history stops being informative about *why* something changed within a release — that reasoning lives in the private issue thread, which the public repo does not carry (decision 1). External pull requests against the public repo cannot be merged directly back into the private repo: there is no shared ancestry between a public-repo commit and any private-repo commit for `git` to reason about, so a would-be contribution has to be re-applied by hand (cherry-pick the diff, re-attribute, re-review) rather than merged. This is the same cost decision 1 names from the issue-visibility side; here it is the same cost from the git-plumbing side.

### 3. No GitHub Actions job pushes to the public repo

The mirror is triggered by a version tag but started by hand (`node ops/release-mirror.js`, no `--dry-run`). Two reasons: a push-scoped credential sitting in Actions secrets for something done a few times a month is exposure with no matching benefit, and an automated path publishes a mistake before a human can stop it — the whole point of gating this on a scan is to give a human the scan's output to read before the push happens, which a scheduled or on-tag Actions job would skip past by construction. `.github/workflows/structural-checks.yml` already runs `node checks/run.js` (and therefore check 7) on every push and PR in the private repo; that is coverage, not the trigger — nothing in that workflow invokes `ops/release-mirror.js`, and none is added by this issue.

### 4. The denylist data file is excluded from the mirror, and from the scan's own file walk

`checks/release-denylist.json` necessarily contains the identifiers it exists to keep out — the whole point of a check is to name what it forbids. Publishing that file to the public mirror would defeat the check entirely: the public repo would carry exactly the private identifiers the issue exists to keep from it. Two mechanisms enforce the exclusion, deliberately duplicated rather than shared through one flag, because they run in two different processes with two different failure costs:

- `ops/release-mirror.js`'s `EXCLUDE_FROM_MIRROR` list removes the data file from the throwaway git index before `git write-tree`, so it is never part of the tree object the mirror commit points at.
- `checks/check-7-release-scan.js` never treats the data file as scan input (`if (relPath === DENYLIST_PATH) continue`) — reading your own denylist as untrusted input would either flag every entry in it as a match against itself, or (once masked) do nothing useful; excluding it is the only sensible reading.

**Absent-data-file behavior, decided and its cost accepted.** The mirror excludes the file *by design*; the check therefore has to handle a run where the file legitimately does not exist (the eventual public-repo CI, once `.github/workflows/structural-checks.yml` is restored there — out of scope for this issue, see issue #148's Standards Notes) without permanently failing. Check 7 resolves an absent data file as **zero findings** (a trivial pass), not an error. This is a **fail-open** choice, and its cost is accepted explicitly: check 7 also cannot tell an intentionally-absent data file (the public mirror) apart from an accidentally-deleted one (a slip in the private repo) — a deletion in the private repo would pass silently too, protected only by `checks/run.js` printing that check 7 ran (visible in the output, not flagged as red).

This fail-open reading is the **check's** alone. `ops/release-mirror.js` itself reads the data file before any network access (`checkDenylistPresent()`) and refuses outright — in both `--dry-run` and a real run — when it is missing, naming the condition. The two are deliberately different: the check has to keep working on the eventual public-repo checkout, where the file's absence is the designed, permanent state; the mirror only ever runs in *this* repo, where the file's absence is always the accidental-deletion case decision 4 names above, and nothing is served by publishing anyway when the script can't confirm what it would be excluding.

**Rejected alternative: fail closed on an absent data file.** This was the first instinct — "no denylist, no proof the tree is clean" is the more conservative reading. Rejected because it does not stay conservative once the public repo's own CI exists: check 7 would then be an unconditional red mark on every push to the public repo, permanently, for a file that is absent *by design* there. A repo-wide check that is always red trains readers to ignore red marks — precisely the failure `CONTRIBUTING.md`'s "When the layer goes red" section warns against, and precisely the failure this repo's own advisory-CI posture (`CLAUDE.md`, "Structural check layer") already lives with once for a different reason. Fail-open costs a narrower, already-mitigated blind spot in the private repo; fail-closed would cost a working check in the public one.

### 5. The credential-shape false-positive rule is a proof, not a path allowlist

The scan must not fire on this repo's own documentation of credential shapes (`ghp_[A-Za-z0-9]{30,}` and similar, quoted verbatim in `skills/work-issue/SKILL.md`, `skills/work-issue/references/subagent-briefs/code-implementer.md`, `skills/work-issue/references/tool-requirements.md` and `docs/audit/git-history-secret-sweep-2026-06-28.md`) while still catching a real, token-shaped secret. A path allowlist (naming those four files as exempt) was rejected outright: it would exempt a real secret that happened to land in one of those files, and it teaches nothing about *why* the exemption is safe.

The adopted rule instead rests on a structural fact: a regex that requires a character class (`[A-Za-z0-9]{30,}`) cannot match the literal bracket-and-brace text that *writes out* that same character class as prose — `ghp_[A-Za-z0-9]{30,}` applied against the string `"ghp_[A-Za-z0-9]{30,}"` fails to match, because the character after `ghp_` is `[`, not an alphanumeric. Check 7 derives its allow-list from exactly this: every credential pattern's own regex source is automatically an allowed literal (`allowedLiterals()` in `checks/check-7-release-scan.js`), masked out of each line before the credential regexes run against it — so a doc line can quote a pattern verbatim without masking a *different*, coincidentally-adjacent real secret on the same line.

**The proof runs on every invocation, not once at review time.** `checks/check-7-release-scan.js` carries a self-test (`SELF_TEST_FIXTURES`) independent of the tree being scanned: for each shape with a fixture, a documented-literal fixture that must NOT match its own regex, and a fake token — built by string concatenation at run time (`'ghp_' + 'A'.repeat(36)`, never written as a literal token-shaped value, which would itself trip this check and the Implementer's own pre-commit secret scan) — that MUST match. A self-test failure throws, which `checks/run.js` reports as a broken check (exit 2), not a tree finding: it means the check can no longer prove the distinction the false-positive AC depends on, which is a defect in the check, not in the repo.

**Known gap: a fixture is hand-written per credential shape, not derived.** `SELF_TEST_FIXTURES` currently lists one fixture per credential id in the seed list (decision 6), a 1:1 match verified by inspection, not enforced by either file. Nothing ties the two lists together mechanically: `selfTest()` iterates `SELF_TEST_FIXTURES`, not the credential list itself, so a credential shape added to `checks/release-denylist.json` with no matching `SELF_TEST_FIXTURES` entry is never visited by that loop at all — not skipped with a warning, simply never reached — and is self-tested for neither half of the proof above. This is a representative, not exhaustive, proof. Closing the gap (e.g. having `selfTest()` iterate the credential list instead and throw on an id with no fixture, turning the drift into a hard signal) is left to a future issue.

### 6. Seeding the denylist: only what the issue evidences, nothing guessed

`checks/release-denylist.json` seeds the two employer-repo checkout paths, three generic filesystem paths (a developer home directory, a root home directory, and a secrets-vault mount point), the employer codename fragment, and the five credential shapes issue #148 names explicitly — none of them written out in this ADR either (see below; the data file is the one place they legitimately live, and it is excluded from the mirror precisely so that remains true). The issue also refers to "an employer repo slug" and "private host names" **without writing them out**, and this ADR does not either. Those two are recorded as a `pending` entry in the data file, naming exactly what is missing and asking the maintainer to fill it in before the first real mirror push — guessing a client identifier risks seeding the wrong one silently, which is worse than a known gap named in the data file the mirror script and the check both already read.

**The mirror enforces this, it does not just ask nicely.** `ops/release-mirror.js` refuses a real (non-dry-run) push outright while `pending` is non-empty, naming each entry's id; `--dry-run` only warns, since a dry run publishes nothing and the warning is how an operator finds out before the first real attempt. "The mirror script and the check both already read" the data file is therefore literal, not aspirational: the mirror reads it for the presence check above, the pending-entries check here, and the exclusion list (decision 4); the check reads it for its scan patterns.

### 7. Version: patch, following the check layer's own precedent

`version_policy` in `AGENTS.md` reserves *minor* for "new skill, new loop-type, new subagent-brief, new AGENTS.md field, changed skill behavior" and *patch* for internal tooling the plugin's shipped-skill runtime behavior does not depend on. The entire five-check structural-check layer — `checks/run.js`, `checks/lib/*.js` and checks 1/2/4/5/6 together — shipped as a **patch** bump (`0.31.2` → `0.31.3`, commit `c1750d5`, #80/#110): none of it changes what a consumer repo's `/work-issue` run does, only what this repo's own `syntax_check` and CI evaluate. Check 7 and `ops/release-mirror.js` are the same class of change — repo-internal tooling, not a shipped skill or a new AGENTS.md field a consumer repo would declare — so this issue follows the same precedent: patch.

### 8. The scan set is the published set: `git ls-files`, not a disk walk

`checks/check-7-release-scan.js` scans exactly `git ls-files` (minus the excluded denylist data file), the same tracked-file source `ops/release-mirror.js`'s `mirroredFileList()` publishes from (minus the same exclusion). A file the mirror ships is therefore always a file this check has scanned, and vice versa — no third, independently-maintained list (e.g. a fixed text-extension allowlist) that the two could drift apart from. This replaces an earlier draft that walked the disk against a fixed extension list: that approach both over-scanned (a gitignored, untracked file like a local `.env` was scanned and could make the check refuse for content that would never be published) and under-scanned (a tracked file whose extension was not on the list was published without ever being scanned). A file without a NUL byte is treated as text; one with a NUL byte is skipped as binary, with the skip counted in the output rather than silently dropped. Where `git` is unavailable or the check is run outside a git checkout at all (a tarball extraction, with no `.git`), the scan falls back to the disk walk it used to always do, and says so — a degraded but working mode, not a silent gap.

## What this ADR deliberately does not name

Per issue #148's own instruction to the implementing loop: this record does not spell out the employer repo slug, the specific employer-repo checkout path fragments, the generic filesystem paths, or any private host name — none of them literally, anywhere in this file. Naming any of them here would defeat the purpose of the check this ADR documents (and, mechanically, check 7 itself catches a literal recurrence of the filesystem paths in *any* tracked file, this one included — see decision 4's absent-data-file discussion for the one file the patterns are allowed to live in). What matters for this decision is the check's *behavior* on that class of value, not the values themselves, and the behavior is fully described above without quoting them.

## Consequences

- `checks/run.js` discovers check 7 with no edit to itself, `AGENTS.md`, or the workflow — the check-layer's discovery contract (`CONTRIBUTING.md`, "Adding a check") is exercised exactly as designed.
- `node ops/release-mirror.js --dry-run` is safe to run at any time: all four refusals evaluate before any network call (the `pending`-entries condition warns rather than refusing in `--dry-run`, see decision 6), and the one network call dry-run makes (`git ls-remote`, to report the prospective parent) is read-only and degrades to `"unknown (no network / no credential)"` rather than failing the dry run.
- The first **real** push is a human act, deliberately: `RELEASE_MIRROR_TOKEN` has to be set locally, HEAD has to be a tagged commit (`--tag` names it explicitly; otherwise `git describe --exact-match --tags HEAD` must resolve one), and the `pending` entries in `checks/release-denylist.json` must be filled in first — the mirror refuses a real push otherwise (decision 6).
- A real run also fetches the public HEAD into the local object store and verifies it against `git ls-remote` before building the commit object (decision 2), and authors that commit from AGENTS.md's `commit_identity` rather than the ambient `git config` — both read at run time, neither hand-copied into this script.
- A future issue restoring `.github/workflows/structural-checks.yml` to the public repo inherits decision 4's fail-open choice for free — check 7 will pass there without modification, on an absent data file, by design.
